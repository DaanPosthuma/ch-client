Building a ClickHouse dev container—then a CHIP-8 emulator in pure SQL

A walkthrough of everything in this environment: the container, the ClickHouse build, the bugs we hit along the way, and the emulator that turned into the main event.

1. The dev container

Everything here runs inside a single Docker container (clickhouse-dev), built from a Dockerfile that layers on top of Ubuntu 24.04: Clang 21, a pinned Rust nightly toolchain, Node.js + the Claude Code CLI, and a pile of quality-of-life tools (gdb, clangd, mold, ripgrep/fd/bat/fzf/git-delta, tmux, htop, neovim, uv). Two named Docker volumes back it: one for /workspace (the ClickHouse checkout and this project), one for /home/dev (so tool configs and command history survive container rebuilds).

The compiler choice mattered more than expected—more on that below.

2. Building ClickHouse from source

The goal was a Debug build (for testing/debugging) and a RelWithDebInfo build (for actually running things at usable speed), both from a from-scratch clone with submodules.

GCC turned out to be a dead end

The original plan was the latest GCC. Partway through, ClickHouse's own build docs revealed that as of early 2026 the project dropped GCC support entirely—only Clang 21+ is supported now. So the container ended up with Clang 21 as the primary compiler, with GCC available separately for other projects.

A Rust toolchain, for a C++ database

ClickHouse vendors a handful of components in Rust (via the corrosion CMake integration): delta-kernel-rs for Delta Lake support, a PRQL compiler, and skim for the fuzzy history search in clickhouse-client. The build pins an exact nightly toolchain in rust/vendor.sh, which had to be installed via rustup before CMake configure would succeed.

Bug #1—io_uring blocked by Docker's seccomp profile. The Debug unit test binary aborted immediately on startup with assertion failed: !r inside contrib/silk/src/fibers/fiber.cpp, at a call to io_uring_queue_init_params. Docker's default seccomp profile blocks the io_uring_* syscalls (a hardening measure against several past kernel CVEs), and ClickHouse's vendored silk fiber scheduler hard-requires it. The WSL2 kernel (6.6.87) supported io_uring fine—this was purely a container syscall filter. Fixed with security_opt: [seccomp:unconfined] in docker-compose.yml, a deliberate trade-off for a single-user local dev container.

Building

Both builds used Ninja + ccache (tuned up to an 80 GB cache) with lld as the linker:

CC=clang-21 CXX=clang++-21 cmake -G Ninja -D CMAKE_BUILD_TYPE=Debug ..
ninja clickhouse unit_tests_dbms

The Debug build produced a 6.7 GB clickhouse binary and a 6 GB unit_tests_dbms; RelWithDebInfo (-O2/-O3 -g -DNDEBUG) came in at 4.8 GB.

3. Running the test suite—and finding a real upstream bug

The unit test binary is a single process running 27,428 gtest cases. One of them, UniqueKeyProbeTest.NewestLiveWinsOverOlder, aborted the entire process outright.

Bug #2—a genuine ClickHouse bug, not ours. Under gdb, the crash traced to DB::abortOnFailedAssertion with the message "UNIQUE KEY probe invariant violated: key at batch row {} is live in more than one part"—an internal chassert invariant (only compiled into Debug builds) failing inside a brand-new, actively-developed "unique key" feature. We'd cloned the literal tip of ClickHouse's dev branch, one day old. Rather than block the whole run on someone else's WIP bug, a small wrapper script (run_unit_tests.sh) runs the suite, detects a process abort, identifies the offending test from the log, adds it to a --gtest_filter exclusion, and restarts—repeating until a run finishes clean.

Final result: 27,427 tests ran, 22,684 passed, 0 failed, 4,743 skipped (mostly tests needing CAP_SYS_NICE, unavailable in an unprivileged container), 3 intentionally disabled microbenchmarks, and the one pre-excluded upstream bug.

4. A Python client, managed with uv

A small project (ch-client) was set up with uv init / uv add, using clickhouse-connect against the RelWithDebInfo server. Eight pytest tests cover connectivity, DDL/DML round-trips, aggregates, parameterized queries, and error handling—all passing against the real, locally-built server.

5. A CHIP-8 emulator, running entirely as SQL

This is the part that took the environment somewhere unplanned. ClickHouse isn't an imperative language: no stored procedures, no WITH RECURSIVE, no loops. Emulating a CPU means finding a way to express fetch–decode–execute as SQL expressions.

The architecture

CPU state (4096-byte memory, 16 registers, I, PC, a 16-level stack, timers, a 64×32 display, 16 keys, and an RNG seed) is a single ClickHouse Tuple. A SQL CREATE FUNCTION ch8_step(state) -> state decodes one opcode and returns the next state. The trick that makes it a real CPU rather than a one-shot function is arrayFold—ClickHouse's array left-fold—which runs ch8_step N times inside a single SQL query:

CREATE FUNCTION ch8_run_batch AS (s, cycles) ->
    ch8_tick_timers(arrayFold((acc, x) -> ch8_step(acc), range(cycles), s));

Every batch of cycles is one INSERT INTO chip8.state SELECT ..., and the state table is an append-only log—one row per batch, ordered by (run_id, step_id). The entire execution history of any run is sitting there as ordinary rows, queryable with plain SQL (see the Explore tab). It felt like the natural way to do this in an OLAP database rather than fighting it.

Pitfall—WITH/subqueries inside a UDF break under arrayFold. The first version of ch8_step used a WITH ... SELECT block for readability (binding mem, pc, op, etc. as local names). Called directly it worked fine. Called from inside arrayFold's lambda, it failed with Not found column acc in block—the subquery loses access to the enclosing lambda's accumulator variable entirely. The fix: no WITH anywhere in the CPU logic. Instead, expensive derived values are computed once and threaded down as explicit function arguments—the SQL-UDF equivalent of a let-binding.
Pitfall—chaining UDF calls directly explodes the query plan. ClickHouse UDFs (CREATE FUNCTION) are macro-expanded at each call site, not opaquely compiled. Nesting ch8_step(ch8_step(s0)) (or aliasing intermediate results with WITH s1 AS ch8_step(s0) and calling ch8_step(s1)) substitutes the entire already-expanded expression tree at every reference—size multiplies at each level, and hit ClickHouse's Query tree is too big. Maximum: 500000 limit after just two steps. Chaining must go through arrayFold, a real runtime loop that compiles the lambda once and applies it repeatedly—never through direct nesting or named intermediate results outside of it.

Opcode coverage

All 35 standard CHIP-8 opcodes are implemented: control flow (JP/CALL/RET, conditional skips), the full 8XY_ ALU family, sprite drawing with XOR/collision and edge clipping, the keypad, timers, BCD conversion, and the block memory ops. A few spec ambiguities were resolved toward the common modern default (SCHIP-style in-place SHR/SHL, I left unchanged by FX55/FX65).

Validation

Rather than trust the SQL by itself, a throwaway reference implementation in plain Python was used to cross-check pixel-for-pixel against the Timendus chip8-test-suite ROMs. The 2-ibm-logo.ch8 test renders correctly, and 3-corax+.ch8—the standard opcode-correctness suite—shows a checkmark next to every single tested opcode, no crosses:

6. This web app

A small FastAPI service (also running in the container, port 8000) ties it together: this page, an interactive ROM runner that steps the emulator frame-by-frame and renders the live display, and a database explorer for querying chip8.state directly and browsing the ch8_* function source.
